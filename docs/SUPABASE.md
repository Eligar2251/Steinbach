# Подключение Supabase

**Это опционально.** Игра полностью работает без облака: сохранения пишутся во встроенную локальную БД `user://saves/hexempire_saves.json` (8 слотов + автосохранение). Подключайте Supabase только если нужны сохранения на нескольких устройствах.

## Удаленный проект

1. Создайте проект в панели Supabase и сохраните database password вне репозитория.
2. Откройте SQL Editor и выполните **целиком** `supabase/migrations/202610070001_initial_schema.sql` один раз.
3. Альтернатива — Supabase CLI:
   ```sh
   supabase login
   supabase link --project-ref YOUR_PROJECT_REF
   supabase db push
   ```
   Если миграция уже выполнена вручную, не запускайте ее повторно через CLI без синхронизации migration history.
4. Authentication → Providers → Email: включите email/password. При включенном Confirm email пользователь сначала подтверждает письмо, затем входит.
5. Authentication → URL Configuration: задайте адрес опубликованной игры как Site URL и разрешенный Redirect URL. Для подтверждения email не нужна передача URL-токена в Godot: после подтверждения можно вернуться и войти паролем.
6. Project Settings → API / API Keys: возьмите HTTPS Project URL и **anon (legacy JWT) или publishable key**. **Не используйте service_role и `sb_secret_*`!**
7. Запустите игру → «Настройки / облако Supabase» → сохраните эти два публичных значения. Они лежат в `user://supabase.json`.
8. Начните партию → «Меню» → «Облако Supabase» → регистрация / вход → «Сохранить в облако».
9. На другом устройстве настройте тот же проект, войдите в тот же аккаунт, начните временную партию и загрузите облачный слот из меню. Загрузка заменит текущую партию после проверки JSON.

Supabase без этого подключения не вызывается. В данной рабочей среде удаленный Supabase не развертывался и HTTP-вызовы к реальному проекту не проверялись.

## Локальный Supabase и тест RLS

Нужны Docker, Supabase CLI и psql:

```sh
supabase start
supabase db reset
psql 'postgresql://postgres:postgres@127.0.0.1:54322/postgres' \
  -v ON_ERROR_STOP=1 -f tests/supabase_rls.sql
```

Тест работает в транзакции и откатывает пользователей/сохранения, проверяя изоляцию двух пользователей, запрет подмены owner_id и отсутствие доступа anon. Используйте только отдельную тестовую БД. Тест не заменяет проверки размера и формы каждого вложенного поля.

Клиент требует HTTPS. Для локального HTTP Supabase используйте доверенный HTTPS reverse proxy либо отдельную dev-only настройку клиента; не ослабляйте TLS-проверку в production. Если игра открыта через удаленный preview, адрес `localhost` в браузере — устройство пользователя, не сервер.

## Схема

- `profiles.id` → `auth.users.id`; профиль автоматически создается триггером, удаляется вместе с auth user. Обновлять разрешено только display_name.
- `game_saves.owner_id` → `auth.users.id`; уникальная пара `(owner_id, slot)`; JSONB `state`, версия формата, timestamps; максимум 1 MiB.
- Серверные constraints проверяют ключи верхнего уровня, версию и базовую форму. Подробная клиентская валидация перед созданием объектов — `GameManager.valid_snapshot()`.
- Все операции таблиц ограничены RLS с `auth.uid()`. Публичный ключ сам по себе не дает читать сохранения.
- Клиент хранит токены только в памяти и обновляет session перед истечением. «Выйти» очищает локальные токены, но не отзывает все серверные сессии аккаунта.

## Безопасность и дальнейшее развитие

Содержимое JSON — недоверенные пользовательские данные, а не честный счет игры. Для рейтинга/мультиплеера нужны серверная модель состояния, валидация команд и серверный подсчет результата. Не публикуйте лидерборд, основанный на клиентском `score`.

Для production также нужны лимиты запросов/числа слотов, политика хранения и удаления данных, восстановление аккаунта, тесты сетевых таймаутов/CORS и полноценное логирование без паролей/токенов. Парольный клиент не получает и не должен получать ключи администратора.
